# JARVIS 第二阶段：对话风格与情绪表达微调设计

日期：2026-10-26。目标：中文对话、动态称呼、体贴且克制的情绪表达；先按效果设计。
状态：设计与参考配置，尚未连接 AutoDL、下载训练底座或启动 GPU 训练。
本目录所有候选样本均未经过用户审核，不能直接当作已验收训练集。

## 1. 推荐路线

先建立“底座 + 角色提示词”的基线，再做 LoRA 监督微调（SFT），根据盲测决定是否追加 DPO 偏好优化。
正式微调候选先用 Qwen/Qwen3-14B；另用 Qwen/Qwen3.5-27B 做效果与响应延迟对照。
这不是声称 14B 一定优于 27B，也不声称选定模型在所有中文对话上最优；最终由本项目固定评测集决定。

Qwen3-14B 为文本生成模型，有官方关闭思考输出的开关，适合先验证低延迟中文对话。
Qwen3.5-27B 也是可选开源权重候选，包含多模态组件。本轮只训练文字时须冻结视觉组件，并使用框架对应的 qwen3_5_nothink 模板，不能直接照搬 Qwen3 的配置。
两者的官方模型卡均标明 Apache-2.0，仍需分别记录权重版本和数据许可。

## 2. 哪些能力由什么负责

- 角色语气、简洁程度、称呼习惯、情绪回应方式：SFT 学习。
- 用户偏好与可更新个人信息：SQLite / 检索上下文。
- 苏州天气、时间、CPU / 内存：实时接口。
- “打开设备”“保存文件”是否真实成功：程序执行结果。
- 语音音色与韵律：TTS；识别准确率：ASR。
- 界面的能量形态：前端状态机与音量，不由语言模型每帧生成。

本轮训练能改善文字情绪表达，不等于训练了语音情感识别器，也不意味着模型拥有人类情绪。现有 emotion.py 的关键词接口仍需要单独的数据、训练和评测，才能换成学习型分类器。

## 3. 数据怎么产生

### 先定义风格

参见 persona_v1.md。先写 100–200 条人工确认的标准会话，覆盖喜欢和不喜欢的回应。
称呼应从运行时偏好读取；不能把所有回答都训练成“先生”。未提供偏好时使用“您”或自然省略称呼。

### 三种来源

1. 人工编写：身份、称呼切换、情绪支持、纠错与能力边界的核心样本。
2. 大模型辅助合成：更强且允许该用途的模型依据场景生成多种候选；记录生成模型、版本和使用许可。
3. 实际交互纠正：收集真实失败案例，脱敏后由人重写成期望回答，再审核入库。

当前 JARVIS 的 mock 回复、报错文字、失败工具调用和未审核的历史回答，不应直接作为优质 assistant 标签。
不会自动导出或上传现有 SQLite 聊天和录音。

### 生产过程

场景设计 → 用户表达与上下文 → 多个回答候选 → 自动过滤 → 人工选择/改写 → 分组去重 → 审核 → 数据版本冻结。

自动过滤检查：
- JSON / 角色顺序正确，最后一个目标回答属于 assistant；
- 消息非空、长度合理、没有密钥/电话号码等真实敏感信息；
- 不混入 mock 文本、影视台词复制、其他模型的自我介绍、模板乱码；
- 不出现缺少执行证据的“已经完成”，不把不确定情绪当成确定事实；
- 去掉大量近似改写和固定开场白重复。

人工复核关注事实、语气、称呼、情绪贴切度、回答是否有具体帮助。自动评分不能替代最终人审。

### 一万条目标样本的建议构成

| 类别 | 条数 | 比例 |
|---|---:|---:|
| 身份、称呼与角色一致性 | 1000 | 10% |
| 日常中文对话、计划与事务协助 | 2500 | 25% |
| 情绪支持、倾听、庆祝与挫败回应 | 2000 | 20% |
| 多轮上下文、称呼变化与记忆上下文使用 | 1500 | 15% |
| 澄清、纠错、不确定性与工具状态边界 | 1500 | 15% |
| 有许可且适配风格的通用能力保留样本 | 1500 | 15% |

条数是会话样本，不是语句数；训练资源应按 tokenizer 后的 token 总量估计。
训练记录可带情绪与场景元数据用于采样和评测，但不能把运行时拿不到的“正确情绪标签”偷偷塞进模型输入。

## 4. 格式与数据分割

采用 messages 会话格式，另存 provenance / review_status / scenario_family_id。
正式送入训练器时导出仅包含 messages 的记录，元数据留在数据清单中。
参见 seed_candidates.jsonl，仅为待审核原创示例。

先按原始会话、场景家族和生成种子分组，再切成约 90% 训练、5% 验证、5% 测试。
同一会话切出的不同窗口、同一个模板的近似改写必须进入同一个分组，避免训练/测试泄漏。
另建立约 300 条由人撰写、训练与合成都不接触的最终盲测题。

长对话需要验证截断：末尾 assistant 回答不能被全部截掉，过长样本应合理分窗。
审核通过的标签优先于纯数量，1 万条是阶段目标，先验证 500–2000 条。

## 5. AutoDL 实例与目录

推荐起步：一张 80GB 显存的 NVIDIA GPU，训练 14B BF16 LoRA，先用 micro-batch=1、4096 上下文和梯度检查点。
48GB 显存可作为后续降配候选，需用相同配置短训实测峰值；24GB 主要考虑 4-bit QLoRA。
这属于工程起步预算，显存峰值受模型结构、长度、框架和优化器影响，未在 AutoDL 实测。
更大的 27B 实验应独立测显存；适配器无法跨不同底座互用。

主机内存建议 64–128GB；数据盘可先预留约 200GB，覆盖底座、缓存、导出与日志。
实际机型、库存、显存、存储容量和计费以 AutoDL 当次页面为准。

Windows 侧文件一直保存在 F:\Javis_os。
AutoDL 为 Linux，远端对应根目录使用 /root/autodl-tmp/jarvis：

    models/       底座和 tokenizer
    datasets/     原始、审核后、分割后数据及清单
    configs/      每次训练配置
    runs/         训练日志、adapter、checkpoint
    exports/      供推理使用的合并模型
    cache/        HF、pip、Torch 等缓存
    tmp/          处理临时文件
    tools/        锁定版本的训练框架
    envs/         训练与推理的独立环境

选择 Python 3.11+ 的 NVIDIA PyTorch 镜像，按模型和框架要求确认 CUDA / PyTorch / transformers 的兼容组合。
不要根据旧教程随意卸载实例驱动。先运行 nvidia-smi、torch.cuda.is_available，再安装训练工具。
训练和 vLLM 推理环境分别建立，验证后保存 pip freeze、框架 git commit、模型 revision。

把 HF_HOME、PIP_CACHE_DIR、TORCH_HOME、XDG_CACHE_HOME、TMPDIR 指向远端项目根目录下子目录。
本地数据盘不能作为唯一备份；训练结果和环境清单需要另存到文件存储或下载到本机。

## 6. 微调步骤

### 第 0 轮：基线

用同一角色规范和同一测试输入，盲测 Qwen3-14B 和 Qwen3.5-27B。
固定思考模式、上下文、采样参数与响应长度，分别比较文本质量、首字延迟和完整语音轮次延迟。
如底座加提示词已达到某类目标，不必为该目标额外增加训练数据。

### 第 1 轮：环境和数据冒烟

审核 300–500 条样本，跑约 20–50 个训练 step：
- 确认只有预期的 LoRA 参数有梯度，底座冻结；
- 解码检查 chat template、EOS、loss mask；
- assistant 标签确实被训练，user 和 system 被遮蔽；
- 没有 NaN、显存溢出或回答被截断；
- 记录峰值显存、实际 token 吞吐、数据加载时间、checkpoint 恢复能力。

这轮用来验证流程，不能据此宣布角色训练成功。

### 第 2 轮：小规模 SFT

用 1000–2000 条审核后的会话做一次 1–2 epoch 的训练，和“底座 + 同样提示词”盲测。
确认风格确实改善，再扩到约一万条数据。

### 第 3 轮：正式 SFT

起始参数建议：
- BF16 LoRA，rank=32、alpha=64、dropout=0.05；
- 训练框架支持的线性层；LlamaFactory 使用 lora_target=all；
- learning_rate=5e-5，可与 1e-4 做一次对照；
- 最大长度 4096，batch=1、gradient_accumulation=16；
- 1–2 epoch，warmup_ratio=0.03，cosine scheduler；
- gradient_checkpointing=true；
- train_on_prompt=false，mask_history=false；
- 初轮 packing=false，先保证会话与 loss mask 正确；
- 保留若干 checkpoint，结合验证损失与盲测选择版本。

参考配置位于 sft_lora_reference.yaml；它不是已经实测的云端配置。
正式数据文件尚不存在，禁止把未审核种子直接导出为正式训练集。
QLoRA 备选是把冻结底座以 4bit 加载，再训练 LoRA 参数，并非“4bit 全参数训练”。

### 第 4 轮：按需 DPO

若 SFT 已会回答，但经常啰嗦、过度恭维、称呼不自然，可收集约 500–2000 组偏好数据。
同一 prompt 包含 chosen 和 rejected 两种回答，并写出偏好理由。
先统一格式，再使用框架 DPO trainer，小学习率实验后仍需通用能力回归测试。
DPO 不是第一轮必需步骤，也不能把自动生成的优劣标签直接当作真实人类偏好。

## 7. 如何验收

候选模型和基线使用相同提示词、采样参数及记忆上下文；输出随机编号，人工盲评。

建议关注：
- 角色一致性、正确称呼及称呼变更后的跟随；
- 情绪回应是否自然，是否理解否定、反讽和“只想倾诉”；
- 具体帮助程度，减少空泛鼓励与固定套话；
- 没有工具结果时是否捏造已经执行；
- 常识、事实、指令跟随能力是否退化；
- 重复、冗长和不必要的思考文本；
- 首字延迟、回答 token 数、整轮语音时延。

可设阶段目标：称呼测试正确率≥98%；人工情绪贴切度平均≥4/5；300 题盲测胜率目标≥65%。
这些是验收目标，不是已达到结果。重要边界案例应逐项审阅，不能用平均分掩盖失败。
ROUGE、BLEU、单一 loss 不能代替角色和情绪质量评估。

## 8. 接回现有 JARVIS

训练后的 adapter 需要对应的精确底座与 tokenizer；部署可加载 adapter，或先合并成独立模型。
用 vLLM 或框架 API 暴露兼容 Chat Completions 的服务，设置服务端鉴权。
桌面端仍使用已有 .env 配置地址、模型名和密钥，示例：

    API_BASE_URL="http://127.0.0.1:18000/v1"
    API_MODEL="jarvis-v1"
    API_KEY="填写自己的服务密钥"
    CHAT_MODE="api"

上面的本机端口可通过 SSH 隧道映射到 AutoDL 推理服务；具体主机与 SSH 端口使用实例控制台提供值。
模型训练好后仍需云端 GPU 推理。训练用实例与长期运行的推理实例可分别规划。
ASR、TTS、情绪分类和硬件执行均按已有独立模块接入，不会因文字微调自动获得新能力。

## 9. 这一阶段的交付顺序

角色规范与 100–200 条人工标准样本 → 300 题盲测框架 → 500 条冒烟数据 →
1000–2000 条小规模 SFT → 结果复核 → 扩充一万条 → 需要时 DPO → 服务与桌面联调。

不能直接把聊天日志全量上传后宣布训练完成。数据生产、审核、训练与评测是相互独立且都需要完成的工作。
